# ADR-003: Session permissions for remote desktop

**Status** — Both directions implemented. Android-to-Windows release validation is ongoing. **Updated** 2026-11-13.

PC controlling Android initially launches **one managed native scrcpy window** using `scrcpy --serial SERIAL` with an exact authorised USB ADB device. Arguments are an allowlist with numeric FPS, bitrate and resolution bounds; no shell commands, wildcards or unsupervised ADB TCP/IP. The scrcpy process must be stopped on Eon exit and must show an error when the target becomes offline. Redistribution requires pinned official Genymobile archive hash and Apache-2.0 notices.

Android viewing/controlling Windows is a separate capture/input service requiring an explicit, time-limited user-approved session on the PC, with clearly visible active indicator and an always available stop control. `remote.view`, `remote.control`, `clipboard`, `power`, `files` are separate capabilities. Never assume Windows lock screen, UAC secure desktop or hidden monitors can be captured or controlled. Stop injection immediately on revoke, inactivity timeout, lock, navigation or lost identity. Monitor/rotation/DPI coordinate transforms need physical tests at 100/125/150% scaling.

Avoid exposing a general command-execution endpoint through remote permissions; only typed, schema-validated actions with per-action ACLs. Video pipeline, hardware codec and data channel should be selected on measured latency, CPU and battery costs, not architectural guesswork.

Eon 2 accepts Android-to-Windows requests only on the paired device's per-serial USB reverse tunnel or the authenticated Tailscale HTTPS listener. The HMAC binds the method, path and body. Windows grants viewing and optional input for one device and one transport for up to 30 minutes. A new transport requires fresh PC approval. The indicator can revoke input while viewing continues or terminate the session. Pairing alone grants neither capability.

The Windows capture process uses WebCodecs to encode the selected monitor. Android devices that advertise an H.264 hardware decoder receive Annex B H.264 when Windows can open the encoder. VP8 is used when Windows cannot initialize H.264 or Android lacks a compatible hardware decoder. Android decodes to a native video surface. Signed control batches travel on a separate HTTP request connection. Encode queues and video response buffers are bounded, and the receiver resumes from a keyframe after skipped video. [Electron desktop capture](https://www.electronjs.org/docs/latest/api/desktop-capturer) · [H.264 WebCodecs registration](https://www.w3.org/TR/webcodecs-avc-codec-registration/) · [Android MediaCodec](https://developer.android.com/reference/android/media/MediaCodec)

The signed `/v1/remote-desktop/` endpoints use `GET status` and `POST request|stream|input|stop`. `stream` returns encoded width and height and the initial input grant as response headers. Each binary packet contains a big-endian 32-bit payload size, a one-byte kind and its payload. Kinds 0 through 4 represent heartbeat, keyframe, delta frame, input revocation and UTF-8 close reason. Only the device and transport that obtained approval can renew the stream lease, send typed input or close the session. Input batches have increasing sequence numbers and a rate limit. Lock, suspend, secure desktop, device revocation, display changes and disconnection terminate sharing and release held input.
